<objective>
Build and defect-prove the PKG-05 measurement, **before** `assertSingleInstance` exists.

Purpose: the ordering is the point. RESEARCH names `assertSingleInstance()` as the phase's hinge —
the first real runtime code in a package that has so far been types plus four frozen constants —
and states that the PKG-05 probe must be written and passing *before* it lands, so the probe's
baseline is a package with genuinely zero runtime dependencies. Written afterwards, the first thing
it ever measures is the new code and there is no clean reading to compare against.

A manifest check ("one dependency, and it is types-only") is what CONTEXT.md rules insufficient:
zero runtime bytes is a claim about what lands in a **consumer bundle**, and a manifest cannot see
inlined vendor code. The probe therefore bundles the built artifact and inspects the module graph,
and keeps the manifest check only as a second, cheaper, more legible signal.
Output: `scripts/pkg05-zero-runtime-deps.mjs`, a `check:deps` root script, a recorded clean
baseline, and mutant P5 observed in both halves.

This plan runs in parallel with plan 02-04 (also wave 3). It transiently mutates
`packages/concierge/package.json` in its own worktree; 02-04 does the same in its own. Neither
leaves a change, so the two cannot conflict.
</objective>

    are live in the source documents:

    - **(a) Dependencies add zero bytes.** REQUIREMENTS.md PKG-05 says *"Core's **runtime dependency
      footprint** is verified to be zero-cost"*; ROADMAP SC-5 says *"Core's **installed dependency
      footprint** is verified to add zero runtime bytes to a consumer bundle."* The word in both is

    edge is real and stays in `dependencies`; what is zero is its *runtime* contribution.

    Create `scripts/pkg05-zero-runtime-deps.mjs` taking `<entry> [manifest]` — entry as
    `process.argv[2]` (no default; fail loudly with a usage message if absent), manifest as
    `process.argv[3]` defaulting to `packages/concierge/package.json`. It makes **two** assertions
    and exits 1 if either fails, naming which one failed:

    **Assertion A — module graph (PKG-05a).** `import { rolldown } from "rolldown"`, bundle the
    entry with `{ platform: "neutral", onwarn() {} }`, `generate({ format: "es" })`, take the chunk,
    and compute `vendored` = keys of `chunk.modules` whose id contains `node_modules`, and
    `externals` = `chunk.imports`. Print both lists on their own labelled lines
    (`vendored modules:` and `unbundled external imports:`) so a failure is legible. Fail if either
    is non-empty. This catches both failure modes independently — inlined vendor code, and an
    unbundled external import edge — so the probe does not rely on a single indicator.

    **Assertion B — manifest byte size (PKG-05b).** Read the manifest's `dependencies`. For each
    entry, resolve its runtime entry point from the manifest's own directory using `createRequire`
    from `node:module` — `createRequire(pathToFileURL(resolve(manifestPath)))` then
    `require.resolve(name)` — `statSync` it, and fail if the size is not 0. Print each dependency
    with its resolved path and byte size. If `require.resolve` throws for an ESM-only dependency,
    fall back to reading that dependency's own `package.json` and resolving `exports["."].default`
    (then `module`, then `main`) relative to its directory, and record in the SUMMARY that the
    fallback was needed.

    On success, print exactly the sentence
    `core's dependencies contribute zero bytes to a consumer bundle` and exit 0. That sentence is
    the locked claim; it is deliberately not `has no deps`.

    Add a root script
    `"check:deps": "node scripts/pkg05-zero-runtime-deps.mjs packages/concierge/dist/index.js"`.
    Keep every existing root script unchanged.

    `rolldown@1.2.0` is a direct root devDependency (installed in plan 02-01) precisely so this
    import resolves under pnpm's strict `node_modules` layout — a transitive copy under `tsdown`
    would not. Confirm `node -e "import('rolldown')"` resolves from the repo root before writing the
    script; if it does not, stop and report rather than switching to a relative path into
    `node_modules/.pnpm`.

    **Record the pre-hinge baseline in the SUMMARY**, this plan's most important output: the count
    of modules in the graph, the vendored count, the unbundled-external count, the resolved path and
    byte size of `@standard-schema/spec`'s runtime entry, and the byte size of
    `packages/concierge/dist/index.js`. Research measured 1 / 0 / 0, a 0-byte
    `@standard-schema/spec` entry, and a 1,034-byte `dist/index.js`. Plan 02-06 compares against
    these numbers.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry → consumer bundle | Any new `dependencies` entry ships bytes into every app that installs this package |
| manifest → artifact | A manifest inspection cannot see vendor code that a bundler has already inlined |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-20 | Tampering | dependency substitution or addition at install time | mitigate | `check:deps` fails the moment a second runtime dependency enters the graph, so an added dependency is visible in CI rather than only in a lockfile diff. Core has exactly one dependency and it has no install scripts. |
| T-02-21 | Tampering | a probe that has never been observed failing | mitigate | P5a and P5b prove each assertion independently. A probe with one untested half would report green while the untested half was broken. |
| T-02-22 | Information Disclosure | inlined vendor code carrying its own transitive surface into consumer bundles | mitigate | Assertion A fails on any module whose id contains `node_modules`, which is the only signal that catches vendoring after bundling. |
| T-02-23 | Repudiation | an ambiguous requirement quietly reinterpreted after the fact | mitigate | Reading (a) is written into the script header and printed as the success sentence, so the claim being made is fixed before the hinge lands and cannot be renegotiated in plan 02-06. |
| T-02-SC | Tampering | npm/pnpm installs | accept | This plan installs nothing. `rolldown@1.2.0` was installed and audited in plan 02-01; `pnpm-lock.yaml` is not in `files_modified`. |
</threat_model>
