<objective>
Prove schema emission against three real published validators, because every claim in this area is
a claim about someone else's package and two of them are claims the documentation gets wrong.

Purpose: CAT-06 exists because `standardschema.dev` says Valibot implements Standard JSON Schema
and valibot 1.4.2 does not — measured twice now, once in Phase 1 and once in this phase's research.
CAT-02 exists because `z.discriminatedUnion` emits `{$schema, oneOf:[…]}` with no root `type`, and
a transport then rejects the entire session update so the agent silently loses every action in that
stage. A hand-rolled fixture would prove only that the check reads a field we ourselves wrote.

Output: `test/emission.test.ts`, and four mutants proved to fire.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party validator → core | `~standard.jsonSchema.input()` is code core calls at module init; it may throw and may return anything. This suite is where that is actually exercised. |
| emitted schema → agent | The emitted JSON Schema is the contract the agent produces arguments against. A silently-wrong root removes an entire stage from the agent's reach. |
| mutation harness → repository working tree | Mutates tracked source and rebuilds a gitignored artifact. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-34 | Denial of Service | a non-object schema root reaching a transport | mitigate | CAT-02 cases 1-3 against real emitters plus mutant M-03-6. `types.ts:22-28` records the downstream symptom: the transport rejects the *entire* session update and the agent apologises that it cannot do that here. |
| T-03-35 | Denial of Service | an emission failure crashing module init | mitigate | Case 9 asserts a throwing validator produces a `CatalogValidationError` with an issue, not the validator's own `TypeError` escaping `buildCatalog`. |
| T-03-36 | Information Disclosure | the vendor name absent from the failure | mitigate | Case 4 asserts the `vendor` field AND the composed message, and mutant M-03-10 proves it. Without the vendor the developer cannot tell whether their declaration is wrong or their validator simply cannot emit. |
| T-03-37 | Tampering | derivation silently winning over the escape hatch | mitigate | Case 6 uses an escape hatch measurably DIFFERENT from what the validator would emit, so the case cannot pass under a reversed ordering; mutant M-03-4 proves it. A same-value escape hatch would make the test green under either order. |
| T-03-38 | Tampering | the output projection shipped to the agent | mitigate | Case 8 pins a measured concrete difference between projections; mutant M-03-5 proves it. A schema with a transform or a default emits a different schema in each direction, and tool calling needs the side the agent must produce. |
| T-03-39 | Tampering | a mutated `dist/` surviving a mutant run | mitigate | `dist/` is gitignored and invisible to both `git status` and the harness's tree-clean check. Explicit `pnpm build` after every mutant, and a full three-gate run as the task's final acceptance. |
| T-03-40 | Denial of Service | a lockfile rewritten under a mutant gate | mitigate | Every gate uses `pnpm --config.verify-deps-before-run=false`. `CI=true` and `--frozen-lockfile` are actively wrong — they produce a vacuously-green PASS. |
| T-03-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing; 03-02 owns the only install and its legitimacy audit (all `[OK]`, no postinstall, exact pins). Gates are configured not to trigger an install. |
