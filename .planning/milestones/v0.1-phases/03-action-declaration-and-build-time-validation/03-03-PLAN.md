    Add to `packages/concierge/src/catalog.ts`:

    `export function buildCatalog<const A extends readonly AnyActionDefinition[]>(actions: A, options?: BuildCatalogOptions): Catalog<A[number]["name"]>`

    **The `const` type parameter is REQUIRED** and is CAT-01's whole mechanism. Measured across 50
    actions: with `const`, `names` derives `"action00" | ... | "action49"`; with a plain
    `readonly AnyActionDefinition[]` parameter it derives `string`. Doc-comment this, and note that
    `tsc` truncates large unions in diagnostics (the 50-name union printed as
    `"action00" | ... | "action13" | ... 35 more ... | "action49"`), so a test asserting on it must
    not expect the full text.

    Body, in this order:

    0. `assertSingleInstance();` as the **first statement**. ROADMAP Phase 3 SC-5. Doc-comment why
       here and not elsewhere: `defineAction` would fire it once per action; module scope does not
       survive `sideEffects: false`; `buildCatalog` is the earliest entry point every consumer
       necessarily reaches.
    1. `const target = options?.jsonSchemaTarget ?? JSON_SCHEMA_TARGET;`
    2. Allocate `issues: CatalogIssue[]`, `diagnostics: CatalogDiagnostic[]`, a `seenNames` set, and
       the entry array. All allocated inside the function body — never at module scope.
    3. Iterate `actions` (this is the package's first loop; `src/` has none today). Per action:
       - **duplicate name** — if already seen, push `duplicate_action_name` with
         `fix: "rename one of them."`. Continue to the next action.
       - **emission** — `emitSchema(action, target)`. On `ok: false`, map `reason` to a code:
         `not_emittable` and `threw` both to `schema_not_emittable`, `root_not_object` to
         `schema_root_not_object`; carry `vendor` onto the issue and compose `problem` from the
         emission's `detail`; supply a `fix` naming the concrete remedy (`supply an explicit
         \`jsonSchema\` on the action` for the first, `wrap the schema in an object, or move the
         union inside a property` for the second). Then continue — an action with no parameters
         cannot produce an entry.
       - **SEC-01, and read this carefully because both halves of the requirement are live, and
         because the obvious emptiness test is wrong.**
         The obvious test is `Object.keys(parameters.properties ?? {}).length > 0`. It is wrong:
         measured (RESEARCH *Pitfall 3*), `z.record(k, v)` emits
         `{type:"object", propertyNames, additionalProperties}` with **no `properties` key at all**,
         so a schema accepting arbitrary caller-supplied keys AND values — the most
         redaction-sensitive shape there is — would be classified EMPTY and silently defaulted to
         `"drop"`. That fails closed against leaks, but it leaves SEC-01's "required at declaration
         time" clause unenforced exactly where it matters most, with the author never asked.
         Ship this instead. A schema is **NON-EMPTY when ANY of these holds**:
           1. `properties` is an object with at least one own key;
           2. `propertyNames` is present;
           3. `patternProperties` is present;
           4. `additionalProperties` is present AND is not `false`.
         Everything else is EMPTY. Three notes, each load-bearing:
           * Condition 4 is `present and not false`, NOT the shorter `additionalProperties !== false`.
             The short form treats an ABSENT key as non-empty, which would flip `z.object({})` — the
             genuinely-empty case — into a build failure. Measure what each of `zodEmptyObject`,
             `arktypeEmptyObject` and `zodRecord` actually emits for this key before shipping, and
             record all three in the summary.
           * Read all four keys through a local `Record<string, unknown>` view of `parameters`, NOT
             through `JsonSchemaObject`'s declared members. `JsonSchemaObject.additionalProperties`
             is declared `boolean`, and the measured `z.record` emission puts a schema OBJECT there —
             the declaration is narrower than reality. Do not amend `types.ts` for this (CONTEXT
             forbids it); record the divergence as a Phase 4 note instead.
           * `Object.keys`, never `for...in` — a hostile emitted schema may carry a polluted
             prototype.
         Then:
           * non-empty properties AND `action.redact === undefined` → push a `redaction_missing`
             ISSUE naming the action, with `fix: "add \`redact: \\\"drop\\\"\` to the declaration, or a projection function if some arguments are safe to record."`
             This is ROADMAP SC-2's third bullet and SEC-01's "required at declaration time" clause.
           * empty properties AND `action.redact === undefined` → resolve to `"drop"` with no issue
             and no diagnostic. This is SC-4's "an unspecified redaction policy drops arguments
             rather than passing them through", scoped exactly as SEC-01 scopes it ("required ...
             for any action with a non-empty schema"). There are no arguments to leak, so failing
             the build would be noise; failing *open* would not be.
         Doc-comment this split explicitly, including the reading of SEC-01 that produces it, so a
         reviewer can disagree with the reading rather than guess at it.
       - **CAT-05** — `action.effects?.destructive === true && action.consent === undefined` → push
         `destructive_without_consent`, one diagnostic per offending action, each naming its action.
         Never an aggregated summary line: that loses the name DX-03 requires.
       - **SEC-05** — `action.readsUntrusted === true && action.consent === undefined` → push
         `reads_untrusted_without_consent`, same shape, distinct code, `fix` stating that a consent
         policy is what makes a human confirm before attacker-controllable content can steer the
         action.
       - Build the normalized action record as a shallow copy with the resolved redaction —
         `{ ...action, redact: action.redact ?? "drop" }`. `buildCatalog` returns a NEW frozen
         catalog rather than mutating its input (CONTEXT lock), and copying means page script
         mutating the original declaration object cannot reach the catalog. `{...action}` copies own
         enumerable properties only, so a `__proto__` key on the input cannot pollute the copy.
    4. `if (issues.length > 0) throw new CatalogValidationError(issues);` — ONE throw carrying every
       issue. Never throw on the first failure: a developer declaring twenty actions should see
       twenty problems in one run, not fix-and-rebuild twenty times.
    5. Dispatch diagnostics AFTER the throw check, through
       `const sink = options?.onDiagnostic ?? defaultDiagnosticSink;` where the module-private
       default formats the diagnostic and calls `warnHost(...)`. A consumer hook that throws is the
       supported mechanism for making a diagnostic fatal in their own build, so the throw
       propagates by design — do not wrap the sink in `try`/`catch`.
    6. Assemble `entries`, `names`, and `byName` (via `Object.create(null)`), then
       `deepFreeze(catalog, skip, new WeakSet())` and return.

    **`deepFreeze`, module-private, and the shallow form is not an alternative.** Measured in ESM
    strict mode: with the array frozen and the elements not, `catalog[0].handler = attackerFn`
    **did not throw** and the replacement handler ran. Signature
    `function deepFreeze<T>(value: T, skip: ReadonlySet<object>, seen: WeakSet<object>): T`. Return
    non-objects and `null` unchanged; return early on anything in `skip` or already in `seen`; add
    to `seen`; `Object.freeze`; then walk `Reflect.ownKeys(value)` reading each descriptor with
    `Reflect.getOwnPropertyDescriptor` and recursing only when `"value" in descriptor` — **never
    read through a getter**, which would run application code during catalog build. `skip` holds
    every `action.schema` reference: freezing a validator's internals is untested and not obviously
    safe, and SEC-03 names the handler, not the validator. Functions fall out at the
    `typeof !== "object"` guard and are not frozen — the record freeze is what stops replacement,
    which is the property SEC-03 asserts. Do NOT use the `Object.isFrozen(value) → return` early-out
    RESEARCH sketched: it skips the children of an already-frozen object, and the escape-hatch
    `jsonSchema` a consumer supplies may be frozen at the top with mutable children.

    **Hand forward to Phase 4:** `frozenArray.filter(...)` returns a NEW, UNFROZEN array, so
    `catalogFor` must re-freeze its filtered result. Write this in the doc comment beside
    `deepFreeze`, not only in the summary — Phase 4 reads the source.
