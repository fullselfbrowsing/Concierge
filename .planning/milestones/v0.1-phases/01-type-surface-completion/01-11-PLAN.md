<objective>
Close CR-02, IN-02, and WR-03: **no real bridge satisfies `B extends Bridge`, so the library's
canonical usage does not compile — and the reason nobody noticed is a naming collision in the same
file.**

`Bridge` (`types.ts:841-847`) defaults both type parameters to `Record<string, never>` — the
**bottom** of each constraint rather than the top. `Record<string, never>` requires every property to
be `never`, so a bridge with any real member is not assignable to it. And that default is precisely
what `BridgeRegistry<B extends Bridge = Bridge>` (`:849`) and `StageDefinition<B extends Bridge = Bridge>`
(`:871`) constrain against. Measured:
`Bridge<{applyFilter: (k: string) => void}, {count: () => number}> extends Bridge` evaluates to
**false**, and `CLAUDE.md`'s own canonical example — "the app exposes verbs like
`applyFilter({key, value})`" — is TS2344.

There is a second, independent half. `ConciergeConfig.stages` (`:1102`) collects `StageDefinition`
at the defaulted `B`, and `B` reaches contravariant positions through `AnyActionDefinition<B>`'s
handler, so a concrete-bridge stage is not assignable to the defaulted one (TS2375). This is the
exact variance problem `AnyActionDefinition` (`:819-825`) was created to solve for `Snapshot` and
`AckPayload`, solved there with `any`, and left unsolved for `Bridge` at the collection site.

**IN-02 is very likely how this stayed invisible, and that is why it lands in the same plan.**
`ActionHandler<Args, Bridge, …>` and `ActionDefinition<Name, Schema, Bridge = unknown, …>` bind a
type parameter *named* `Bridge`, shadowing the exported interface of the same name inside those
declarations. Meanwhile `BridgeRegistry<B extends Bridge>` and `StageDefinition<B extends Bridge>`
use `B` and refer to the real interface. A reader scanning `ActionDefinition`'s unconstrained
`Bridge = unknown` sees a parameter that accepts anything and does not connect it to the broken
constraint five hundred lines away. Two spellings for two different things in one file.

**WR-03 is the coverage half.** `actions.test-d.ts:195` instantiates `ActionDefinition`'s bridge
parameter as `null` — the one argument that collapses `Bridge | null` to `null` — so `_handlerBridge`
at `:204` asserts `Equals<Ctx["bridge"], null>` and cannot observe the `| null` at all, while its
doc comment claims it does. Measured: `types.ts:302` `bridge: Bridge | null` → `bridge: Bridge`
**escapes**, and `types.ts:852` `read: () => B | null` → `read: () => B` **escapes**. That contract
is load-bearing — `types.ts:301` says "Always check it", `:851` says "`null` when no component has
registered", and `FailureReason` carries `no_bridge` (`:148`) as the code for exactly this state.

**This is the last free moment.** Changing `Bridge`'s defaults after publish is a breaking change for
anyone who wrote `Bridge` bare. Phase 1's goal is "the remaining defects that would become breaking
changes after publish are closed", and this is one — it survived the 19-mutation battery because
**nothing in the suite ever instantiates `Bridge` with a member**, so both type parameters were
exercised only at their broken defaults.

Purpose: make the bridge story usable at all, and remove the naming ambiguity that hid it.
Output: two type-argument defaults, one erasure at the collection site, three renamed type
parameters, and the coverage that would have caught all of it.
