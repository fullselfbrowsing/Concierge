<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → npm registry | Publish authority crosses here; whatever proves identity is the highest-value target in the repo |
| repository secrets → workflow env | A long-lived token in scope silently outranks OIDC |
| CI green signal → release decision | Gates that do not run, or run in the wrong order, produce a trusted-but-empty signal |
| workspace membership → publish set | Private fixture packages must never become publish candidates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-46 | Spoofing / Elevation | publish-token exfiltration from CI | mitigate | npm trusted publishing over OIDC with `id-token: write`; **no `NPM_TOKEN` anywhere in the repository or in this workflow's env**, asserted by a repo-wide grep. Trusted-publisher configuration binds publish rights to a specific repo and workflow rather than to a transferable secret. |
| T-02-47 | Repudiation | silent provenance downgrade | mitigate | A stray `NPM_TOKEN` makes publish succeed *without* an attestation — green build, degraded artifact, invisible from the exit code. `RELEASING.md` records that a successful publish without an attestation is to be treated as a failed publish, and requires a human to check the npm page on the first release. |
| T-02-48 | Tampering | dependency substitution at install time in CI | mitigate | `pnpm install --frozen-lockfile` in both workflows; `pnpm --version` asserted to be 11.x so the lockfile is read by the package manager it was written by. |
