<objective>
Close defect (b): `readbackHash` has no producer in the contract. Declare the readback presentation
seam — a sink the app calls with what it rendered, returning a **receipt** rather than a bare hash
string — plus the injected digest stand-in and the inbound server-challenge brand.

Purpose: a bare `=> Promise<string>` makes canonicalization an app bug with a verified collision —
`JSON.stringify({amount: 4180, coupon: undefined})` is byte-identical to
`JSON.stringify({amount: 4180})`, so two semantically different payloads hash the same. That is the
gate failing while appearing to work, which is the exact failure class this milestone exists to
prevent. Carrying the canonical bytes alongside the hash is WebAuthn's own reason for making
`clientDataJSON` opaque: intermediaries must not parse-and-reserialize.
Output: `Readback`, `ReadbackReceipt`, `ReadbackSink`, `DigestLike`, `ServerChallenge`, and the
first half of `consent.test-d.ts`.

**Serial phase.** Plan 4 of 9 in a single serial sequence. Do not parallelize.

**Scope fence — Phase 1 ships the TYPES only.** The JCS (RFC 8785) canonicalizer (~40 LOC) and the
hand-rolled UTF-8 encoder (~15 LOC) land in Phase 8 with the consent kernel. Do not implement them
here. Do not bundle SHA-256 in core. Do not declare `ReadbackAttestation` — D-12 item 1 defers it to
Phase 8, which designs the kernel that consumes it.
</objective>

    Add five declarations, placed in the consent section near `SnapshotNormalizer`.

    **`Readback<Payload>`** — the sink's input: the `payload` core snapshot-compares, plus an
    optional `presented` carrying the literal string the app put on screen. JCS canonicalization runs
    over `{payload, presented?}`, binding both. Document that this follows Secure Payment
    Confirmation, which hashes the *structured values that were displayed*, not pixels.

    **`ReadbackReceipt`** — exactly four fields: `hash`, `alg`, `canonicalization`, `canonical`.
    Type `alg` as the literal `"SHA-256"` and `canonicalization` as the literal `"JCS"`, so the
    receipt is self-describing and a type test can assert them; widening either later is additive.
    Document that `canonical` is carried alongside `hash` deliberately — WebAuthn's reason for making
    `clientDataJSON` opaque bytes — so Phase 8's confirm and any future server verification re-read
    these bytes rather than re-deriving them, and note that JCS (RFC 8785) is owned by core and lands
    in Phase 8.

    **`ReadbackSink`** — the **generic-function** form, copying `SnapshotNormalizer`'s shape exactly:
    a single type alias whose right-hand side is a generic function taking `Readback<P>` and
    returning `Promise<ReadbackReceipt>`. It must NOT be a defaulted generic alias
    `ReadbackSink<Payload = unknown>`.

    The justification carried in from discussion was **wrong and has been corrected** — read the
    D-03 callout. Neither form accepts a payload-specific app sink; that was never the discriminator.
    The real difference is *type preservation across the call*: with a defaulted alias,
    `ConciergeConfig.presentReadback?: ReadbackSink` instantiates `P` to `unknown` at the field and
    core loses the payload type at every call site, while a generic function infers `P` per call.
    The testable consequence is that a generic function rejects a type argument
    (`ReadbackSink<Booking>` is TS2315) and a defaulted alias accepts one.

    The `ReadbackSink` doc comment carries a mandatory ergonomics sentence: **write your sink
    generically — it is called with every payload type your app reviews.** A payload-specific sink is
    rejected with a confusing contravariance message, and without this sentence it becomes a support
    burden identical to the `snapshotEquality` trap the file already documents.

    **`DigestLike`** — a structural stand-in for the platform `SubtleCrypto`, following
    `AbortSignalLike` verbatim. One member, `digest`, declared with **METHOD syntax**, taking the
    literal `"SHA-256"` and `ArrayBuffer | ArrayBufferView`, returning `Promise<ArrayBuffer>`.

    Method syntax is load-bearing and was verified against both real platform typings. The browser
    DOM lib defines `BufferSource` as `ArrayBufferView<ArrayBuffer> | ArrayBuffer`; `@types/node`
    defines it as a union of concrete typed-array types. Only method-parameter bivariance bridges
    both — every function-property form fails against at least one of them with TS2322. Do NOT add
    `@types/node` or the DOM lib to this repo to check this; it was probed in an isolated sandbox and
    the result is recorded.

    **The deliberate asymmetry — state it in BOTH doc comments.** `DigestLike` requires method
    syntax; `ConsentPolicy.snapshotEquality` must stay **function-property** syntax. Under method
    syntax `snapshotEquality`'s parameters become bivariant, a `(a: Booking, b: Booking)` comparator
    silently assigns to `ConsentPolicy<unknown>`, and the Success-Criterion-7 guard stops guarding —
    with no symptom except one unused directive that a reviewer would "fix" by deleting the test.
    Add a sentence to each declaration saying its syntax is deliberate, naming the other as the
    deliberate opposite, and warning that a reviewer who normalizes the two breaks one of them.
    These two seams sit near each other and this is genuinely counter-intuitive.

    **`ServerChallenge`** — a branded string: a module-private `declare const` of type
    `unique symbol` intersected onto `string`. Do NOT export the brand symbol;
    `isolatedDeclarations` emits it correctly as a module-private `declare const`. Document that it
    is opaque, server-issued, client-echoed, and **never minted here in v0.1**. The brand is the
    mechanism, not decoration: it makes `const forged: ServerChallenge = "i-made-this-up"` a TS2322,
    so D-05's produce-nothing rule is compiler-enforced rather than merely documented. Cite the
    concrete reason: an echoed-but-unstored challenge provides no replay protection at all
    (GHSA-gjjc-pcwp-c74m), so page JavaScript has no minting authority worth trusting.
    Do not add it to `ConsentAck` in this plan — that is Plan 05, the hinge.

    Finally, extend `DeliveryReport.readbackHash`'s doc comment to name `ReadbackSink` and
    `ReadbackReceipt` as its producer, closing the loop that currently dead-ends.

    Do not touch `ConsentAck` in this plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app-rendered bytes → consent artifact | What the human actually saw must bind to what the kernel later compares |
| core → platform crypto | Core has no `crypto`, `TextEncoder`, or `btoa` under `lib: ["ES2022"]`; the digest crosses in from the app |
| server → client (inbound only) | A challenge is issued elsewhere and echoed here; nothing is minted in page JavaScript |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-10 | **Tampering** | canonicalization of the readback payload | mitigate | Core owns the rule (JCS, RFC 8785) rather than the app, and the receipt carries the `canonical` bytes so no verifier re-serializes. `JSON.stringify({a:1,b:undefined})` is byte-identical to `JSON.stringify({a:1})` — a verified collision that would make two different payloads hash the same. Declared in Phase 1 as the literals `"JCS"` and `"SHA-256"`; the encoder is Phase 8. |
| T-01-11 | Tampering | core hand-rolling SHA-256 or UTF-8 | mitigate | Do not. `DigestLike` is injected, never implemented (ASVS V6 by delegation). Asserted by a grep for `sha256`/`TextEncoder`/`btoa` returning 0. D-03 rejected bundling; the "keeps `dispatch` synchronous" argument does not hold because arming happens on delivery via `deferUntilDelivered`, which is already callback-shaped. |
| T-01-12 | **Spoofing / Repudiation** | `ServerChallenge` minted in page JavaScript | mitigate | Brand it with a module-private `unique symbol` so an app cannot construct one without an explicit cast (verified TS2322). Reserve the **inbound** seam only; produce nothing in v0.1. A client-supplied challenge accepted as proof is GHSA-gjjc-pcwp-c74m exactly. |
